# Правила работы с проектом

## Подход

- Сохранять простую структуру FastAPI + Pydantic v2 + синхронный SQLAlchemy + SQLite.
- Выполнять работу небольшими логическими блоками. Объяснять изменения и результаты проверок на русском языке.
- Сначала предлагать следующий шаг, затем проверять наработки и текущие изменения. Писать запрошенные фрагменты кода по прямой просьбе.
- Не перезаписывать пользовательские изменения, не относящиеся к текущей задаче.
- Напоминать о коммите завершённого блока. Создавать коммит и отправлять изменения только по запросу пользователя.

## Структура кода

- Модели таблиц размещать в `app/models.py`, схемы и валидацию запросов в `app/schemas.py`.
- Расчёты и правила переходов статусов размещать в `app/services.py`, HTTP-обработчики в `app/routes.py`.
- Проверку HMAC держать в `app/security.py`, загрузку начальных тарифов в `app/seed.py`.
- Использовать типы, понятные названия и форматирование Ruff. Не добавлять абстракции и зависимости без необходимости для задачи.

## Бизнес-правила

- Все суммы хранить и рассчитывать целыми числами в копейках. Не использовать `float` для денег.
- `amount` означает итог к оплате, `discount` означает размер скидки. Промокод `KVITTO10` даёт 10% скидки без учёта регистра.
- Для рассрочки допустимы 3, 6 и 12 месяцев. Сумма графика должна точно совпадать с `amount`, остаток распределять по одной копейке в первые платежи.
- Для карты и СБП возвращать `null` в `installment_months` и `schedule`.
- Новый платёж создавать в статусе `pending`. Разрешать только `pending -> succeeded`, `pending -> failed`, `succeeded -> refunded`.
- Запрещённый переход, включая переход в тот же статус, должен возвращать `409 {"error": "invalid_transition"}` без изменения записи.
- Сохранять стандартные ошибки валидации FastAPI с кодом `422`; отсутствующий платёж возвращать с кодом `404`.
- Повторный `Idempotency-Key` должен возвращать прежний платёж с `200`, первое создание с `201`. Сохранять уникальность ключа в базе и обработку конфликта вставки через `rollback()` и повторный поиск.

## База и подпись

- Получать сессию для HTTP-обработчиков через `get_db`. Выполнять `commit()` явно при сохранении изменений.
- Изменения схемы оформлять миграциями Alembic и проверять сгенерированный код. Не создавать таблицы через `create_all()` при запуске приложения; в тестах это допустимо.
- Повторная загрузка тарифов не должна создавать дубликаты или изменять существующие тарифы.
- Проверять HMAC-SHA256 по исходным байтам тела запроса до изменения статуса. Не пересобирать JSON перед проверкой подписи.
- Использовать `hmac.compare_digest`. При отсутствии или неверной подписи возвращать `401`.
- Читать секрет из `WEBHOOK_SECRET`. Не записывать реальные секреты в код, логи, Git или Docker-образ. В `.env.example` оставлять только демонстрационные значения.
- Не использовать рабочую базу для автоматических тестов.

## Проверки

При изменении Python-кода выполнять:

```text
python -m ruff check .
python -m ruff format --check app tests migrations
python -m pytest -q
```

При изменении схемы дополнительно проверять миграции на отдельной пустой базе через `alembic upgrade head` и `alembic check`.

- Добавлять тесты для изменённой бизнес-логики. Проверять данные ответов и сохранённые значения в базе, а не только HTTP-коды.
- Для идемпотентности проверять отсутствие дублей; для отклонённых вебхуков проверять сохранение прежнего статуса.
- Не скрывать ошибки проверок и не ослаблять тесты ради успешного результата.
- При изменении запуска или поведения API обновлять README. В AI_LOG описывать только реально выполненную работу и замеченные ошибки.
